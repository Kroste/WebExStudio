# WebExStudio

**Визуальное настольное приложение для создания и выполнения веб-автоматизаций** — сценарии работы браузера моделируются в виде графа узлов (в стиле Node-RED) и выполняются напрямую через [Playwright](https://playwright.dev/dotnet/). Интерфейс: [Avalonia UI](https://avaloniaui.net/).

## Что умеет WebExStudio?

- **Визуальный редактор потоков**: размещение узлов перетаскиванием, соединение их связями (wires).
- **Настоящие ветвления и циклы**: у `if`/`foreach`/`for_range`/`get_links` есть реальные выходные порты (напр. `then`/`else`) — весь сценарий виден в связях, ничего не спрятано в невидимых вкладках.
- **Подузлы**: именованные, переиспользуемые подпрограммы (как функции), вызываемые узлом `call`.
- **Поток данных payload**: единый общий объект данных проходит через поток; подстановки `{key}` / `{payload.key}` заменяются везде.
- **Выполнение в реальном времени**: во время запуска вид автоматически следует за активным узлом (в том числе внутрь подузлов) и подсвечивает его.
- **Узел debug с паузой**: показать payload в журнале и при желании приостановить поток для проверки.
- **Свои подписи**: каждый узел получает произвольное отображаемое имя; плюс чисто комментирующие/заголовочные узлы (`label`/`caption`).
- **Свободный выбор браузера**: Chromium/Firefox/WebKit, системный браузер (Chrome/Edge), свой путь к исполняемому файлу и драйверу.
- **Импорт устаревшего**: старые проекты Python WebEX (вложенные `actions/*.json`) преобразуются в единый поток v2.

## Быстрый старт

### Требования

- [.NET 10 SDK](https://dotnet.microsoft.com/download)
- Браузеры Playwright (установить один раз, см. ниже)

### Запуск

```bash
dotnet run --project WebExStudio.UI
```

### Установка браузеров Playwright (один раз)

```bash
dotnet build WebExStudio.Engine
pwsh WebExStudio.Engine/bin/Debug/net10.0/playwright.ps1 install
```

Также можно использовать уже установленный системный браузер (напр. Google Chrome) в [настройках](#настройки).

### Сборка

```bash
dotnet build          # вся солюшн (WebExStudio.slnx)
```

## Ключевые понятия

### Поток, вкладки и подузлы
- **Поток** — это единый JSON-документ (версия 2) с несколькими **вкладками** и всеми **узлами**.
- Вкладка **Main** — точка входа. Выполнение начинается со всех узлов без входящих связей (узлы входа).
- **Подузлы** — это именованные, переиспользуемые вкладки (напр. `login`, `configuration.general.identification`). Они вызываются **по имени** узлом **`call`** — узел `call` сразу показывает имя подузла. **Двойной щелчок по узлу `call`** в потоке открывает связанный подузел вкладкой.

### Узлы, порты и связи
- У каждого узла обычно **один вход сверху** и **выходы снизу**.
- **У управляющих узлов несколько выходов**:
  - `if_then_else` → `then` / `else`
  - `foreach` → `элемент` (на элемент) / `готово`
  - `for_range` → `цикл` / `готово`
  - `get_links` → `на ссылку` / `готово`
- **Связь (wire)** вы тянете от выходного порта одного узла ко входному порту другого. Выполнение следует за связями.

```
        ┌───────────────┐
        │ ❓ Если/То/Иначе│
        └──●(then)──●(else)┐
           │          │
   ┌───────▼──┐   ┌────▼─────┐
   │ 🖱 Клик   │   │ 🚪 Заверш.│
   └──────────┘   └──────────┘
```

### Payload (поток данных)
- Есть **одно** общее хранилище данных: **payload**. Оно проходит через поток; каждый узел может читать/писать.
- Оно задаётся, напр., узлом **`function`/Начало** (начальные значения в JSON) или через **`set_payload`**.
- **Подстановки** в полях заменяются: `{key}` **и** `{payload.key}` обе берут значение из payload.

### Аннотации
- **`caption`** (крупный заголовок) и **`label`** (текст-комментарий) — это чисто отображаемые узлы без функции — они игнорируются при выполнении.
- Кроме того, у **каждого** узла есть необязательная **подпись**, которая отображается под названием типа (напр. узел клика с подписью «Кнопка входа»).

## Справочник узлов

> Для выбранного узла описание **и** пример отображаются справа в панели свойств.

> **Обработка ошибок (каждый узел):** в панели свойств в разделе *«Обработка ошибок»* можно задать для каждого
> узла **повторы при ошибке** (`retry`, 0 = выкл.) и **задержку между попытками** (`retry_delay_ms`). Если узел
> завершается ошибкой, он повторяется до `retry` раз (с паузой); только после этого путь считается ошибочным.
> Прерывание (Остановить) и `quit` никогда не повторяются — удобно для нестабильных страниц/сети (напр. шаткий
> `goto` или `get_value`).

### Начало
| | Тип | Имя | Назначение | Пример |
|---|---|---|---|---|
| 🚀 | `function` | Вход | Точка входа/старта; задаёт начальный payload (JSON). | `payload = {"host":"https://example.com"}` → `{payload.host}` |

### Навигация
| | Тип | Имя | Назначение | Пример |
|---|---|---|---|---|
| 🌐 | `goto` | Перейти | Перейти по URL, дождаться загрузки. При `new_tab = true` открыть в новой вкладке и переключиться (заменяет `open_tab`). | `url = {payload.host}/login` · `new_tab = true` |
| ✖ | `close_tab` | Закрыть вкладку | Закрыть текущую вкладку. | — |
| 🔗 | `get_links` | Собрать ссылки | Собрать ссылки; выход **на ссылку** выполняется на каждое совпадение. | `selector = a.product` → `{link}` |

### Взаимодействие
| | Тип | Имя | Назначение | Пример |
|---|---|---|---|---|
| 🖱 | `click` | Клик | Клик по элементу (с прокруткой/повтором). Для кнопок загрузки `expect_download = true` → ждёт загрузку и сохраняет её. | `selector = a.download, expect_download = true` |
| ⌨ | `send_keys` | Ввести текст | Ввести текст в поле (заполняет его). Для Enter/Tab/Escape → `press_key`. | `selector = input[name=q], value = {payload.searchword}` |
| ⏳ | `wait_for` | Ждать элемент | Ждать видимости/наличия. | `selector = .result, state = visible` |
| 💤 | `sleep` | Пауза | Ждать фиксированное время. | `seconds = 2` |
| 📋 | `menu_path` | Навигация по меню | Пройти по иерархическому меню (клик/наведение). | `path = Файл, Экспорт, PDF` |
| ↕ | `scroll` | Прокрутка | Прокрутить вверх/вниз или к элементу; многократная прокрутка подгружает «ленивый» контент. | `to = bottom, times = 3` |
| ⏎ | `press_key` | Нажать клавишу | Нажать (специальную) клавишу/комбинацию (Enter, Escape, Tab, `Control+A`), глобально или на элементе. | `key = Enter, selector = input[name=q]` |
| ▼ | `select_option` | Выбор в списке | Выбрать запись в `<select>` по значению/label/индексу. | `selector = select#country, by = label, value = Германия` |
| 👆 | `hover` | Наведение (hover) | Навести мышь на элемент (показать меню/подсказку). | `selector = .menu-item` |

### Поток управления
| | Тип | Имя | Выходы | Пример |
|---|---|---|---|---|
| ❓ | `if_then_else` | Если / То / Иначе | `then` / `else` | `condition = element_exists, selector = .error` |
| 🔄 | `for_range` | Цикл For | `цикл` / `готово` | `start = 1, end = 5` → `{i}` |
| 🔁 | `foreach` | Цикл Foreach | `элемент` / `готово` | `items = {payload.targets}` |
| 📞 | `call` | Вызвать подузел | 1 | `target = login` (показывает имя подузла) |
| ⏸ | `noop` | No-op / точка останова | 1 | Заполнитель |
| ✔ | `assert` | Проверка / Assert | 1 | `condition = element_exists, selector = .success` (ошибка, если не выполнено) |
| 🚪 | `quit` | Завершить | 0 | Останавливает поток здесь |

**Условия `if_then_else` и `assert`** (`condition`): `element_exists`, `element_visible`, `element_text`, `page_title`, `page_url`, `page_contains`, `page_matches` (regex), `payload_equals`, `payload_contains`. Инвертировать через `negate = true`; трактовать значение как regex через `regex = true`. `assert` прерывает путь с сообщением об ошибке, если условие **не** выполнено (необязательный `message`).
Для условий `payload_*`/`ctx_*` **ключ payload** указывается в `selector`, а значение сравнения — в `value` (напр. `selector = visited`, `value = {payload.link}` → проверяет, содержит ли `visited` ссылку). Если `selector` пуст, вместо него используется поле `key`.

### Данные
| | Тип | Имя | Назначение | Пример |
|---|---|---|---|---|
| 📖 | `get_value` | Прочитать значение | Значение из DOM (текст/атрибут) в payload. | `selector = .price, ctx_key = price` → `{price}` |
| 📦 | `set_payload` | Задать payload | Задать ключ в payload. | `key = status, value = ok` → `{payload.status}` |
| 🐞 | `debug` | Отладочный вывод | Payload/контекст в журнал; при желании **пауза**. | `source = payload, pause = true` |
| 📄 | `read_file` | Прочитать файл | Файл в payload. | `path = data.txt, ctx_key = content` |
| 💾 | `write_file` | Записать файл | Записать значение в файл. | `path = out.txt, value = {payload.result}` |

### Дополнительно
| | Тип | Имя | Назначение | Пример |
|---|---|---|---|---|
| ⬇ | `download_url` | Скачать URL | Скачать файл по URL. | `url = {payload.host}/file.pdf` |
| 📸 | `screenshot` | Снимок экрана | Сохранить страницу/элемент в PNG (путь → `screenshot_path`). | `selector = .card, path = receipt.png` |
| ƒ | `page_function` | Function | JS-функция в контексте страницы: без селектора `payload => { … }`, с селектором `(element, payload) => { … }`. Возврат → `ctx_key` (одно значение) или поля объекта сливаются в payload. Изменять страницу (показать подсказку, удалить/выделить элементы) или читать значения. (Объединяет прежний `eval_js`, сохранён как псевдоним.) | `code = payload => ({ count: document.querySelectorAll('a').length })` |
| 🔐 | `save_session` | Сохранить сессию | Записать cookies + localStorage в файл. | вставить после входа; пустой путь = `session.json` |
| 🔐 | `credential_store` | Хранилище (учётные данные) | Маркер/якорь для зашифрованного хранилища учётных данных (двойной щелчок открывает управление). Доступ везде через `{secret[name].user/.password/.api}`. | поместить в Main |
| 🔓 | `use_session` | Использовать сессию | **Если/Иначе для сессий** (2 выхода `загружено` / `нет сессии`): если файл сессии (не слишком старый) существует, его cookies загружаются в работающий браузер → выход `загружено`; иначе `нет сессии`. Так: при сессии сразу переходить, иначе вход + `save_session`. | `max_age_hours = 0` (без ограничения) |
| 🎬 | `download_stream` | Захват потока/медиа | Записывает сетевой трафик, обнаруживает URL медиа (видео/аудио, HLS `.m3u8`, DASH `.mpd`) → payload (`ctx_key`); скачивает прямые файлы по HTTP, сегментные потоки через **ffmpeg**. Потоки с DRM скачать нельзя. | `wait_ms = 8000, download = true` |
| 🤖 | `captcha_guard` | Защита от CAPTCHA | Обнаружить CAPTCHA, автоматически кликнуть первый флажок (`auto_click`), ждать решения. `timeout_s = 0` = без ограничения (ждёт до решения или до «Остановить»). | `auto_click = true, timeout_s = 120` |

### Пример 2 — Итерация по списку (foreach + распаковка payload)

Узел `function` предоставляет **список объектов**. `foreach` распаковывает для каждого элемента его поля в payload (`{payload.host}`, `{payload.name}`); выход **элемент** (порт 0) ведёт в тело цикла, выход **готово** (порт 1) выполняется после.

![Пример 2](docs/images/example-2.png)

```json
{
  "version": 2,
  "tabs": [{ "id": "main", "label": "Main", "isSubFlow": false }],
  "nodes": [
    { "id": "f1", "type": "function", "tabId": "main", "label": "Устройства", "x": 80, "y": 40,
      "config": { "payload": "{ \"targets\": [ {\"name\":\"A\",\"host\":\"10.0.0.1\"}, {\"name\":\"B\",\"host\":\"10.0.0.2\"} ] }" },
      "wires": [["fe"]] },

    { "id": "fe", "type": "foreach", "tabId": "main", "x": 80, "y": 160,
      "config": { "items": "{payload.targets}", "ctx_key": "target" },
      "wires": [["g1"], []] },

    { "id": "g1", "type": "goto", "tabId": "main", "label": "Открыть устройство", "x": 80, "y": 300,
      "config": { "url": "https://{payload.host}/" }, "wires": [["d1"]] },

    { "id": "d1", "type": "debug", "tabId": "main", "x": 80, "y": 420,
      "config": { "source": "payload", "label": "{payload.name}" }, "wires": [[]] }
  ]
}
```

> Примечание: `wires` — это список **по выходному порту**. У `foreach` два порта → `[["g1"], []]` означает: порт 0 (элемент) → `g1`, порт 1 (готово) → ничего.

### Пример 3 — Ветвление с повторным слиянием (if then/else → rejoin)

После `if` в **обоих** случаях продолжаем к следующему шагу: подключить оба выхода (then/else) к следующему узлу.

![Пример 3](docs/images/example-3.png)

```json
{
  "version": 2,
  "tabs": [{ "id": "main", "label": "Main", "isSubFlow": false }],
  "nodes": [
    { "id": "g1", "type": "goto", "tabId": "main", "x": 80, "y": 40,
      "config": { "url": "https://example.com" }, "wires": [["if1"]] },

    { "id": "if1", "type": "if_then_else", "tabId": "main", "label": "Баннер cookies?", "x": 80, "y": 160,
      "config": { "condition": "element_exists", "selector": "#accept" },
      "wires": [["c1"], ["done"]] },

    { "id": "c1", "type": "click", "tabId": "main", "label": "Принять", "x": 320, "y": 280,
      "config": { "selector": "#accept" }, "wires": [["done"]] },

    { "id": "done", "type": "sleep", "tabId": "main", "label": "продолжить", "x": 80, "y": 400,
      "config": { "seconds": "1" }, "wires": [[]] }
  ]
}
```

Ход: `if1` → **then** (`#accept` существует) кликает и идёт к `done`; **else** идёт прямо к `done`. Оба пути сходятся в `done`.

Узел, который будет выполнен **следующим**, **обведён голубым** — так вы видите, какой узел выполнится на следующем шаге (и можете заранее изменить его значения в панели свойств; они применятся при выполнении).

## Payload и подстановки

- **Один** общий объект данных (`payload`) проходит через поток.
- **Задание**: `function` (начальный JSON), `set_payload`, `get_value`, `read_file`, переменные цикла (`foreach`/`for_range` пишут свой ключ; `foreach` по объектам дополнительно распаковывает все поля).
- **Использование**: в (почти) каждом текстовом поле через подстановки:
  - `{host}` **или** `{payload.host}` — обе берут одно и то же значение payload.
- Пример: `goto.url = {payload.host}/login`, `sleep.seconds = {payload.seconds}`, `send_keys.value = {payload.user}`.

## Хранилище учётных данных (секреты)

Учётным данным **в открытом виде** не место в потоке. Вместо этого они хранятся **зашифрованными** внутри потока
и ссылаются только по имени.

- **Хранение**: **по потоку** — в виде зашифрованного блоба прямо в потоке (поле `credentials` в `.json`),
  **AES-256-GCM** с ключом, производным от вашего **мастер-пароля** (PBKDF2). Так **поток и пароли остаются
  вместе** и путешествуют как единое целое; пароли потока A **никогда** не попадают в поток B. (Раньше: один
  глобальный файл для всех потоков — сохранённые там данные нужно вводить заново для каждого потока.)
- **Управление**: панель **🔐 Хранилище** (или двойной щелчок по узлу `credential_store`). Для каждой записи
  (напр. `F95`, `Pixeldrain`) создать поля **пользователь / пароль / API-ключ**. Изменения записываются в поток и
  сохраняются сразу (если у потока уже есть путь к файлу — иначе при следующем сохранении).
- **Использование**: через подстановки `{secret[name].user}`, `{secret[name].password}`, `{secret[name].api}` —
  напр. в **Ввести текст** (`value`), **Перейти** (`url`), **Выбор в списке**, **Клик** (текст).
  В этих полях панель свойств дополнительно предлагает меню **«🔐 Вставить секрет…»**, которое сразу вставляет
  подходящую подстановку (как только хранилище разблокировано).
- **Жизненный цикл**: по умолчанию **заблокировано**. При запуске потока (если используются секреты) появляется
  **запрос мастер-пароля**; после этого хранилище разблокировано на сессию. При **Новый/Загрузка** потока оно
  **заново привязывается к потоку** (и при этом блокируется), а также при **выходе из программы**.
- **Безопасность**: значения секретов разрешаются **только при использовании** и **никогда не попадают в payload**
  (даже через `set_payload`/`function`) — поэтому узел **debug** никогда не показывает значение. В
  **журналах/трассировках** они **маскируются** (`***`). Защита действует против передачи/репозитория/журналов — не
  против злоумышленника с разблокированной сессией или мастер-паролем (приложение должно расшифровывать значения во
  время выполнения).
- У настроек программы **собственная** защита: **ключ API ИИ** и **пароль прокси** в `settings.json`
  хранятся **в зашифрованном виде** (Windows: DPAPI для пользователя; Linux/macOS: AES с привязкой
  к машине и учётной записи), никогда в открытом виде. Значения из старых версий переносятся
  автоматически при следующем запуске. Это защищает от передачи файла конфигурации (вложение в
  обращение в поддержку, резервная копия, снимок экрана) — но не от злоумышленника, у которого
  уже есть ваша учётная запись.

## Настройки

Через **⚙** в заголовке. Сохраняются в `~/.config/WebExStudio/settings.json`
(в Windows `%AppData%\WebExStudio\settings.json`) и загружаются при старте. Окно
разделено на **Браузер**, **Сеть** и **ИИ**.

![Настройки](docs/images/settings.png)

**Язык.** Интерфейс многоязычный (Deutsch, English, Français, Русский; с флагом страны и собственным названием
языка). Язык переключается вверху настроек и применяется **сразу** (без перезапуска) — включая палитру узлов,
панель свойств, контекстное меню и имена/описания/примеры всех узлов. Сохранённый `type` узла и формат потока
остаются неизменными, поэтому потоки взаимозаменяемы независимо от языка. Другие языки добавляются ещё одним
файлом `Localization/<code>.json` в проекте `WebExStudio.Core`.

**Вкладка «Браузер»**

| Параметр | Значение |
|---|---|
| **Тип браузера** | `chromium` (по умолчанию), `firefox`, `webkit`. |
| **Системный браузер (канал)** | пусто = встроенный; `chrome`, `msedge`, `chrome-beta`, `msedge-beta` = установленный системный браузер. `brave` запускает Brave как Chromium (путь к программе ищется автоматически; тип браузера должен быть `chromium`). |
| **Путь к исполняемому файлу браузера** | пусто = автоматически; иначе путь к EXE браузера (`ExecutablePath`). |
| **Путь к драйверу Playwright** | только если драйвер не найден автоматически (задаёт `PLAYWRIGHT_DRIVER_PATH`). Под ним ссылка на ручную/офлайн-установку браузеров (напр. за корпоративным прокси). |
| **Путь загрузки по умолчанию** | целевая папка для загрузок браузера; пусто = `~/Downloads`. Запускайте кнопку загрузки узлом `click` + **`expect_download = true`**: узел ждёт загрузку и сохраняет её туда под **настоящим именем** (иначе Playwright кладёт её лишь временно с именем-GUID и удаляет при закрытии). |
| **Без интерфейса** | запускать браузер без видимого окна. |
| **Запускать развёрнутым** | открывает видимое окно браузера развёрнутым (`--start-maximized`) и позволяет странице использовать всю площадь окна (вместо фиксированного 1280×720). Действует только для браузеров на базе Chromium (Chromium/Chrome/Edge/Brave) и не в режиме без интерфейса. Применяется ко всем вкладкам запуска, в том числе открытым через `open_tab`. |
| **Повторно использовать сессию** | при старте загружает сохранённую сессию (cookies + localStorage) из **файла сессии** (пусто = `session.json` в папке проекта) в контекст браузера. **Внимание:** если поток затем всё равно выполняет шаги входа, это может мешать (вы уже вошли). Для потоков с шагами входа лучше **оставить этот параметр ВЫКЛ.** и использовать узел **`use_session`**, который ветвится во время выполнения (сессия есть → переходить, иначе → вход + `save_session`). |

**Вкладка «Сеть» (прокси)** — действует **на браузер и на запросы ИИ**:

| Параметр | Значение |
|---|---|
| **Прокси-сервер** | напр. `http://proxy.company.com:8080`; пусто = без прокси / по умолчанию системы. |
| **Исключения / обход** | хосты без прокси через запятую (`localhost, 127.0.0.1, *.internal`). |
| **Пользователь / пароль** | необязательно, для прокси с аутентификацией. |

**Вкладка «ИИ»** — см. [ИИ: поток из описания](#ии-поток-из-описания).

**Системный трей.** Сворачивание главного окна (кнопкой `—` в заголовке) убирает WebExStudio
в системный трей вместо панели задач. Значок трея предлагает **Показать** (также по левому
щелчку) и **Выйти**; закрытие крестиком `✕` по-прежнему завершает приложение как обычно. Если
рабочая среда не поддерживает трей (сервер без интерфейса, некоторые Wayland-композиторы без
Status-Notifier), сворачивание откатывается к стандартному поведению — без сообщения об ошибке.

**Проверка обновлений.** Окно **О программе** автоматически проверяет GitHub Releases при
открытии (без блокировки, с учётом прокси — использует системный прокси и учётные данные по
умолчанию, поэтому работает и за корпоративным Kerberos/Negotiate-прокси). Если доступна новая
версия, появляется кнопка `📥 Открыть страницу релиза`, которая открывает
`github.com/Kroste/WebExStudio/releases/latest` в браузере — никакой тихой автоустановки,
вы сами решаете, когда и как обновляться. Кнопка `🔄 Проверить обновления` инициирует новую
проверку по требованию. Ошибки (нет сети или прокси) только журналируются, диалог не показывается.

## Журналирование

NLog пишет в каталог пользовательских данных — `~/.config/WebExStudio/logs/`
(в Windows `%AppData%\WebExStudio\logs\`). Намеренно **не** рядом с исполняемым файлом:
в запущенном AppImage и при системной установке этот каталог доступен только для чтения,
и приложение молча не вело бы журнал вообще.

| Файл | Содержимое |
|---|---|
| `info.log` | Уровень info (ход, старт узла, targets …) — также в цвете на консоли. |
| `debug.log` | Уровень debug для `WebExStudio.*` (подробно). |
| `error.log` | Ошибки со стеком вызовов. |
| `cli-debug.log` | То же для консольного запускателя `webex` (без дублирования в консоль). |
| `cli-error.log` | Ошибки консольного запускателя со стеком вызовов. |

Секреты (ключи API, пароли, токены) **маскируются в каждой строке журнала** (`***`) — централизованно
в конвейере NLog, а не в каждом месте вызова, поэтому забытое место ничего не выдаст.

Необработанные исключения (в том числе из обработчиков событий интерфейса) перехватывает глобальный обработчик: они записываются с уровнем **Fatal** в `error.log` и показываются в диалоге ошибки — приложение по возможности продолжает работу.

Во время выполнения статус узлов и вывод `debug` также появляются в реальном времени в **журнале выполнения** внизу приложения. По каждой записи:

- **Двойной щелчок** → переходит к соответствующему узлу в редакторе (открывает его вкладку, выделяет и центрирует вид).
- **Правый щелчок** → «↪ Перейти к узлу», «📋 Копировать строку» (в буфер обмена) и «💬 Отправить в чат с ИИ» (передаёт тип узла, **ID узла**, статус и сообщение об ошибке как вопрос в чат с ИИ — ID позволяет ИИ однозначно найти узел в автоматически приложенном JSON потока).
- Текст сообщения выделяется и поэтому напрямую копируется.

## ИИ: поток из описания

Кнопка панели **🤖 Поток ИИ** позволяет сгенерировать полный поток из описания на естественном языке. Шаги:

1. Ввести описание (напр. «Открой example.com, войди, прочитай заголовок и запиши его в файл»).
2. ИИ получает **каталог узлов как схему** (производную от `NodeCatalog`) и отвечает JSON потока.
3. Результат **проверяется `FlowValidator`** перед загрузкой. Если он валиден, он попадает прямо на холст
   (как несохранённый поток для проверки). При ошибках проверки они отображаются; при желании поток можно открыть
   через **«Всё равно загрузить»** для ручного исправления.

**Поставщики** (выбираются в **Настройках ⚙**, ключ сохраняется в `settings.json` **в зашифрованном виде**):

| Поставщик | Модель по умолчанию | Примечание |
|---|---|---|
| `anthropic` | `claude-sonnet-4-6` | Anthropic Messages API, нужен API-ключ. |
| `openai` | `gpt-4o` | OpenAI chat completions, нужен API-ключ. |
| `gemini` | `gemini-2.0-flash` | Google Gemini (Generative Language API), нужен API-ключ. |
| `perplexity` | `sonar` | Perplexity (совместим с OpenAI), нужен API-ключ. |
| `ollama` | `llama3.1` | Локальный экземпляр (URL по умолчанию `http://localhost:11434`), без ключа. |

Модель и базовый URL переопределяются для каждого поставщика. Подключение инкапсулировано в проекте
`WebExStudio.AI` через интерфейс `ILlmClient` — другие поставщики можно добавить там, не меняя генератор.

**Автопоиск локального ИИ:** кнопка **🔍 Найти локальный ИИ** (Настройки → ИИ) по нажатию проверяет
распространённые локальные серверы LLM и автоматически заполняет поставщика, базовый URL и найденную модель —
**Ollama** (`localhost:11434`, напр. через Pinokio), а также **совместимые с OpenAI** серверы **LM Studio**
(`1234`), **llama.cpp** (`8080`) и **Jan** (`1337`). По возможности через эти известные порты; нестандартные
порты вводятся вручную.

### Чат с ИИ

Кнопка панели **💬 Чат с ИИ** открывает окно чата с ИИ (несколько ходов, история сохраняется). Можно задавать
вопросы о WebExStudio или итеративно разрабатывать поток. Если ответ содержит поток, под ним появляется кнопка
**«📥 Загрузить в редактор»** — поток (как в диалоге Поток ИИ) сначала проверяется, затем загружается. Кроме
того, как только последний ответ содержит поток, **прямо над полем ввода появляется закреплённая панель
загрузки** — так загрузка остаётся доступной даже при очень длинных ответах (без прокрутки до конца сообщения).
Чат использует те же настройки поставщика и прокси.

С **каждым** сообщением чат получает **текущее состояние потока** (включая промежуточные изменения узлов),
поэтому запросы на изменение опираются на реальный поток, а возвращённый поток можно загрузить напрямую.

### Объяснить поток

Кнопка панели **🧾 Объяснить** заставляет ИИ кратко изложить **текущий поток** понятным языком (обзор, шаг за
шагом по связям, возможные риски). Объяснение появляется в окне чата; поток передаётся модели в фоне, так что
можно сразу задавать уточняющие вопросы.

### Предложение узла

Выберите узел и нажмите **💡 Предложить**: ИИ предлагает — на основе всего потока — **следующий разумный узел**
(тип, подпись, конфигурацию, обоснование). Предложение проверяется по каталогу узлов; через **Добавить** оно
создаётся под выбранным узлом и автоматически соединяется с его выхода.

Флажок **«Предложение узла»** в **строке состояния** (внизу) включает/выключает функцию (настройка сохраняется).
Строка состояния также показывает текущий статус, имя потока, активную вкладку, число узлов и поставщика ИИ.

### Подсказки ИИ (известные проблемы и решения)

На вкладке настроек **«ИИ»** есть поле **«Известные проблемы и решения»** — короткий, самостоятельно
поддерживаемый список (по одной подсказке в строке). Если включён переключатель **«Отправлять подсказки ИИ»**,
эти подсказки прикладываются к **каждому** запросу ИИ (создать поток, чат, объяснить, предложить) дополнительно к
потоку. Так можно зафиксировать однажды решённые проблемы и учитывать их автоматически в будущем. Держите
подсказки короткими, чтобы ИИ мог их хорошо использовать.

В **чате с ИИ** у каждого ответа есть кнопка **«📌 Запомнить как подсказку»** — она добавляет (сокращённый)
ответ прямо в список подсказок (затем редактируется в настройках).

## Плагины (свои узлы)

Свои типы узлов можно подгружать как плагины — без пересборки приложения.

**Написать плагин:**
1. Создать библиотеку классов (`net10.0`), ссылающуюся на **`WebExStudio.Core`** и **`WebExStudio.Engine`**.
2. Для каждого узла реализовать `IActionHandler` (`string Type` + `ExecuteAsync(ExecutionContext, FlowNode)`)
   и предоставить `NodeDefinition` (метаданные для палитры/свойств).
3. Реализовать класс с **`INodePlugin`** (конструктор без параметров), который возвращает оба как
   `NodePluginNode(Definition, Handler)`.

```csharp
public sealed class MyPlugin : INodePlugin
{
    public IEnumerable<NodePluginNode> CreateNodes() =>
    [
        new(new NodeDefinition { Type = "my_hello", DisplayName = "Привет", Category = "Plugins",
                                 Description = "…", Example = "…",
                                 Properties = [ new() { Key = "text", Label = "Текст", Kind = PropertyKind.Text } ] },
            new MyHelloHandler()),
    ];
}
```

При желании пометить целевую версию API, чтобы загрузчик предупреждал о несовместимости:
```csharp
[assembly: WebExStudioPlugin(PluginApi.Version)]
```

Если узел должен **ветвиться** сам (несколько выходов, как if_then_else), задайте в `NodeDefinition`
`OutputPorts`/`OutputLabels` и **`RoutesOutputs = true`**; тогда обработчик маршрутизирует через
`ctx.FollowOutput(node, port)`.

**Поставляемые плагины** (в [`samples/`](samples), они же шаблоны):

- [`samples/FileCheckPlugin`](samples/FileCheckPlugin) — узел **«Файл существует?»** (`file_exists`): ищет в
  папке (пусто = папка загрузок) имя/шаблон и ветвится **найдено / не найдено** — удобно, чтобы перед загрузкой
  проверить, существует ли файл (пример **ветвящегося** узла, `RoutesOutputs`).
- [`samples/HttpRequestPlugin`](samples/HttpRequestPlugin) — узел **«HTTP-запрос»** (`http_request`):
  отправляет REST/webhook-запрос **без браузера** (метод, заголовки `Имя: значение` по строке, тело).
  Тело ответа → `ctx_key` (по умолчанию `response`), код состояния → `status_key` (по умолчанию `response_status`);
  при желании **ошибка при статусе ≥ 400**. `{secret[..]}` допустим в URL/заголовках/теле и разрешается
  **только при отправке**, никогда не журналируется (пример правильной работы с секретами в плагинах).

Собрать и скопировать DLL:
```bash
dotnet build samples/HttpRequestPlugin -c Release
# скопировать HttpRequestPlugin.dll + HttpRequestPlugin.deps.json в %AppData%/WebExStudio/plugins, перезапустить приложение
```

**Загрузка:** поместите скомпилированную DLL в папку `plugins/` — рядом с приложением **или** в
`%AppData%\WebExStudio\plugins` (Linux/macOS: `~/.config/WebExStudio/plugins`). При старте она загружается в
**изолированном контексте загрузки** (`AssemblyLoadContext`): общие хост-сборки (WebExStudio, System, Avalonia,
NLog) используются совместно с приложением, собственные зависимости берутся из `*.deps.json` плагина — так
библиотеки плагинов не конфликтуют с библиотеками приложения. Узлы появляются в **палитре, панели свойств,
проверке** и доступны **ИИ**.

**Управление:** **Настройки → вкладка «Плагины»** показывает найденные плагины со статусом и позволяет
**включать/выключать** (действует после перезапуска), а также открывать папку плагинов.

> **Безопасность:** плагины — это **произвольный код с полными правами приложения** (браузер, файлы, сеть) —
> загружайте только доверенные плагины; песочницы нет. Существующий тип узла не перезаписывается. Своих
> редакторов свойств (пока) нет — только имеющиеся типы полей.

## Командная строка (CLI / без интерфейса)

Потоки можно выполнять **без графического интерфейса** — идеально для `cron`/планировщика задач, CI или
серверов. Проект **`WebExStudio.Cli`** создаёт команду **`webex`** и использует **те же плагины, то же хранилище
учётных данных и тот же валидатор/исполнитель**, что и приложение.

Готовые бинарники `webex` прилагаются к каждому **релизу GitHub** как **отдельный ассет**
(`webex-<version>-linux-x64.tar.gz` ��ли `webex-<version>-win-x64.zip`) — или соберите сами:

```bash
dotnet build WebExStudio.Cli -c Release          # собирает исполняемый файл "webex"

webex run      -f projects/f95zone/f95zoneV2.json -c '<пароль-хранилища>'   # выполнить (по умолчанию без интерфейса)
webex validate -f flow.json                       # только проверить (без браузера)
webex secrets  -f flow.json                       # какие записи {secret[..]} нужны потоку?
```

**Опции для `run`:**

| Опция | Действие |
|---|---|
| `-f, --flow <путь>` | Путь к файлу потока (обязательно) |
| `-c, --credential <пароль>` | Пароль хранилища. Лучше: переменная окружения `WEBEX_VAULT_PW` или интерактивный ввод — пароль в аргументе попадает в историю shell/список процессов. |
| `--var key=value` | Начальное значение в контексте payload (можно несколько раз) → параметризовать поток |
| `--headful` | Запускать браузер видимым (иначе без интерфейса) |
| `--browser <имя>` | `chromium` (по умолчанию), `firefox`, `webkit` |
| `--timeout <ms>` | Тайм-аут по умолчанию на действие |
| `--download-dir <d>` | Целевая папка для загрузок |
| `--out <файл.json>` | Записать отчёт о запуске (статус узлов, ошибки) в JSON |

**Коды выхода** (для cron/CI): `0` ОК · `1` ошибка выполнения (узел завершился ошибкой) · `2` проверка/вызов ·
`3` хранилище (пароль отсутствует/неверен) · `130` прервано (Ctrl+C).

Хранилище разблокируется, только если поток действительно использует `{secret[..]}`. Перед каждым запуском
выполняется проверка, как в GUI (ошибки прерывают). Узлы ИИ (`ai_query`) в CLI не активны.

## Импорт устаревших проектов

Старые проекты Python WebEX (папка с `actions/*.json`, вложенными ссылками `call`/`then_actions_file` и `targets.json`) преобразуются в единый поток v2.

**В приложении:** панель **♻ Конвертировать** → выбрать старую папку проекта → сконвертированный поток загружается прямо в редактор (затем проверить и сохранить).

**Через командную строку:**

```bash
dotnet run --project WebExStudio.UI -- --convert <папкаУстаревшегоПроекта> <выход.json>
# Пример:
dotnet run --project WebExStudio.UI -- --convert projects/usv2 projects/usv3/flow.json
```

При этом:
- каждый ссылающийся файл `.json` становится **именованным подузлом** (имя = путь с точками, напр. `configuration.general.datetime.daylightSavings`);
- `call` / `then_actions_file` / `else_actions_file` становятся видимыми **узлами `call`**;
- `if` становится узлом с **выходами then/else**, ветви снова сливаются к следующему шагу;
- `targets.json` попадает списком в узел **`function`/Начало**, **`foreach`** итерирует по нему → вызывает подузел `start`.

Результат (`projects/usv3/flow.json`) вы открываете через **📄 Открыть поток**.

## Формат файла (v2)

Поток — это **один** JSON-файл:

```json
{
  "version": 2,
  "tabs": [
    { "id": "main", "label": "Main", "isSubFlow": false },
    { "id": "t1",   "label": "Login", "isSubFlow": true, "name": "login" }
  ],
  "nodes": [
    {
      "id": "n1",
      "type": "goto",
      "tabId": "main",
      "label": "Главная страница",
      "x": 80, "y": 40,
      "config": { "url": "{payload.host}" },
      "wires": [ ["n2"] ],
      "seqIndex": 0
    }
  ]
}
```

- **`tabs`**: `main` (`isSubFlow=false`) + именованные подузлы (`isSubFlow=true`, уникальный `name`).
- **`nodes[].wires`**: `wires[portIndex]` = список ID целевых узлов на этом выходе. `if`/`foreach` используют индексы 0 и 1.
- **`nodes[].config`**: все поля, специфичные для узла, в виде строк (числа/булевы тоже строками).
- **`nodes[].label`**: произвольно выбранная подпись (отображается на узле).
- Вызовы подузлов: узел `call` с `config.target = <имя-подузла>`.

## Проверка потоков

`FlowValidator` (в `WebExStudio.Core`) проверяет документ потока на структурные и схематические ошибки — как
страховочную сеть для импортированных и (в будущем) автоматически сгенерированных потоков.
Он возвращает список находок со степенью **Error** или **Warning**;
`IsValid` равно `true`, пока нет ошибок.

**Ошибки** (поток так не выполнится надёжно):

| Код | Значение |
|---|---|
| `unknown-type` | Тип узла не известен в каталоге. |
| `missing-required` | Отсутствует обязательное поле (псевдонимы учитываются). |
| `dangling-wire` | Связь указывает на несуществующий ID узла. |
| `cross-tab-wire` | Связь ведёт к узлу на другой вкладке (разрешено только через `call`). |
| `wire-invalid-port` | Связь на выходе, которого у типа узла нет. |
| `wire-into-no-input` | Связь ведёт в узел без входа (напр. аннотацию). |
| `call-target-missing` | Узел `call` ссылается на неизвестный подузел. |
| `duplicate-node-id` | ID узла встречается несколько раз. |
| `duplicate-subnode-name` | Имя подузла назначено несколько раз (цель `call` неоднозначна). |
| `unknown-tab` | Узел ссылается на неизвестную вкладку. |
| `no-main-tab` | Нет главной вкладки. |

**Предупреждения** (подозрительно, возможно намеренно): `no-entry-node` (вкладка без точки старта / цикл),
`group-missing-node`, `group-foreign-node`.

**При выполнении:** перед каждым запуском поток проверяется. Если есть **ошибка**, запуск **вообще не
стартует** — находки появляются в панели журнала, первый ошибочный узел помечается красным и вид переходит к его
вкладке. **Предупреждения** также показываются в журнале, но не блокируют запуск.

Поставляемые примеры потоков в `projects/` автоматически проверяются валидатором через
`ExampleFlowsValidateTests`.

| `WebExStudio.Engine.Tests` | `ExecutionContext` (payload/подстановки), `ActionRegistry`, обработчики (без браузера) и **выполнение по связям** (ветка if, цикл foreach). |
| `WebExStudio.UI.Tests` | Логика `FlowEditorViewModel` (узлы/связи/подузлы/вкладки/группы, без отрисовки) и **блокировка по проверке перед запуском**. |
| `WebExStudio.AI.Tests` | **Генератор потоков ИИ** (prompt → разбор → проверка) с фиктивным клиентом и выбор поставщика в `LlmClientFactory` — без сети. |
| `WebExStudio.Cli.Tests` | Разбор аргументов runner без интерфейса `webex` (`Options.Parse`: команды, флаги, `--var`, случаи ошибок). |

Тесты движка выполняются **без браузера** — узлы, требующие Playwright, обходятся через условия на основе payload. Тяжёлые по браузеру/вводу-выводу пути (обработчики Playwright, перетаскивание, команда `run` в CLI) юнит-тестами не покрываются; вместо этого проверяется базовая логика (напр. `Options.Parse`, `SecretReferenceScanner`, `ViewTransform`).

### GitHub Actions

[`.github/workflows/ci.yml`](.github/workflows/ci.yml):

1. **`test`** — собирает солюшн (Release) и выполняет `dotnet test` (при каждом push/PR).
2. **`release`** — выполняется **только по тегу `v*` или вручную** (*workflow_dispatch*) и только если тесты зелёные — **не** при каждом push (экономит хранилище артефактов). Создаёт **автономные сборки в один файл** для **Linux (`linux-x64`)** и **Windows (`win-x64`)** — по одному пакету для **GUI** (`WebExStudio-…`) и для **CLI** (`webex-…`) — плюс для Linux дополнительно **AppImage** (`WebExStudio-…-x86_64.AppImage`, собирается через [`build/make-appimage.sh`](build/make-appimage.sh)).
3. По **тегу `v*`** (напр. `git tag v1.0.0 && git push --tags`) все пакеты (GUI + CLI + AppImage, по платформам) дополнительно прикрепляются как **отдельные ассеты** к **релизу GitHub**. **AppImage** — самый удобный вариант загрузки для Linux: сделать исполняемым и запустить (`chmod +x WebExStudio-*.AppImage && ./WebExStudio-*.AppImage`).

## Структура проекта

| Проект | Описание |
|---|---|
| `WebExStudio.Core` | Модели данных (`FlowDocument2`, `FlowNode`, `FlowTab`, `NodeCatalog`), сериализация (`FlowSerializer2`), конвертер устаревших проектов (`LegacyImporter`). |
| `WebExStudio.Engine` | Исполнитель потоков (обход связей), интеграция с Playwright, обработчики действий, трассировка. |
| `WebExStudio.UI` | Настольное приложение Avalonia: холст, отрисовка узлов/связей, палитра, панель подузлов, свойства, трассировка, настройки, о программе. |
| `WebExStudio.Cli` | Runner без интерфейса `webex` (`run`/`validate`/`secrets`) — выполнять потоки без GUI (cron/CI). |
| `WebExStudio.AI` | Подключение ИИ: экспорт схемы узлов, построение prompt, `FlowGenerator` и поставщики (`ILlmClient`: Anthropic/OpenAI/Ollama). |

Технологии: **.NET 10**, **Avalonia 12.1**, **Microsoft.Playwright 1.61**, **NLog 6**, тесты на **xunit.v3**.
